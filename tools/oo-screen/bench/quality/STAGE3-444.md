# Етап 3 — колір 4:4:4 для тексту: дослідження (СИМУЛЯЦІЯ)

> **СИМУЛЯЦІЯ, НЕ ВИМІРЮВАННЯ НА РЕАЛЬНОМУ ЗАЛІЗІ.** Синтетичний корпус `bench/corpus` (8 кадрів, 1080p/1440p),
> конвеєр емулюється в numpy + ffmpeg (libx264, libvpx-vp9) на Linux. Немає Windows-захоплення, MF MFT,
> декодування у браузері. Числа придатні лише для порівняння варіантів між собою.

Відтворення: `python3 run444.py` (код — `avc444.py`, тести — `test_avc444.py`).

## Методика

- RGB → Y'CbCr BT.709 limited, 8 біт, кадр доповнюється до кратного 16.
- 30 однакових кадрів @30 fps, CBR-подібно (`b = maxrate = bufsize`), оцінюється останній декодований кадр.
- **Базовий 420 Main**: libx264 Main, veryfast, zerolatency, chroma 2×2 box, на приймачі білінійний апсемпл.
- **A — AVC444 (2× Main)**: розкладка MS-RDPEGFX 3.3.8.3.2 (YUV420p combination for YUV444):
  головний вид = Y + U/V у парних позиціях (B1–B3); допоміжний вид: Y-площина — у кожному 16-рядковому
  блоці рядки 0–7 = непарні рядки U444, 8–15 = непарні рядки V444 (B4, B5); U/V-площини = U444/V444
  на парних рядках, непарних стовпцях (B6, B7). Обидва види — звичайні 4:2:0, libx264 Main.
  Бітрейт ділиться 70 % / 30 % (main/aux).
  **Відхилення від RDP**: (1) chroma головного виду береться точково (без фільтра), тому розклад/збирання
  без кодека — точно без втрат (перевіряє `test_avc444.py`); у RDP-клієнтах (FreeRDP) U[2y,2x] може
  відновлюватися як 4·avg − 3 інші з евристикою обрізання; (2) aux-вид кодується щокадру, хоча RDP
  (AVC444v1/v2, поле LC) дозволяє слати його рідше; (3) фіксований поділ бітрейту; (4) AVC444v2
  (інша розкладка aux) не моделювалась.
- **B — 420 + lossless chroma-тайли**: базовий потік 420 Main + одноразово (для статичного екрана)
  повнороздільні Cb/Cr 16×16-тайлів, що містять текст (маска як у Stage 0), упаковані у смугу та
  стиснуті PNG. Приймач підміняє декодовану chroma у цих тайлах. Байти — «one-shot kbit».
- **C — VP9 profile 1 4:4:4**: libvpx-vp9 `-profile 1 -deadline realtime -cpu-used 8 -row-mt 1 -lag-in-frames 0`.
- Метрики: PSNR по Y та середнє по Cb/Cr (у просторі Y'CbCr з відновленого RGB), SSIM по luma, text
  edge-SSIM (див. RESULTS.md), kbit/кадр (фактичний розмір потоку / 30), час кодування ffmpeg на кадр
  (включно з накладними витратами процесу, лише для порівняння).

## Результати (середнє по 8 кадрах корпусу)

| варіант | luma PSNR dB | chroma PSNR dB | SSIM | text edge-SSIM | kbit/кадр | one-shot kbit | кодування ms/кадр |
|---|---|---|---|---|---|---|---|
| 420 Main (базовий) @4M | 45.25 | 39.28 | 0.9901 | 0.9932 | 100 | 0 | 12.9 |
| A AVC444 2×Main @4M | 41.87 | 45.22 | 0.9720 | 0.9808 | 105 | 0 | 26.9 |
| B 420 + lossless chroma-тайли @4M | 47.51 | 68.81 | 0.9901 | 0.9938 | 100 | 763 | 14.5 |
| C VP9 p1 4:4:4 @4M | 55.58 | 59.61 | 0.9997 | 0.9995 | **201** | 0 | 23.7 |
| 420 Main (базовий) @8M | 50.43 | 39.96 | 0.9989 | 0.9987 | 157 | 0 | 13.2 |
| A AVC444 2×Main @8M | 50.34 | 51.81 | 0.9969 | 0.9978 | 175 | 0 | 25.5 |
| B 420 + lossless chroma-тайли @8M | 56.06 | 72.63 | 0.9991 | 0.9994 | 157 | 763 | 13.0 |
| C VP9 p1 4:4:4 @8M | 57.39 | 61.26 | 0.9998 | 0.9997 | 227 | 0 | 21.6 |

Найгірший кадр для 4:2:0 — `colortext-*` (червоний/синій текст): chroma PSNR базового 32.0–33.5 dB,
A 35–42 dB, B 62–68 dB, C 53–57 dB. Повна таблиця по кадрах — у виводі `run444.py`.

Спостереження:
- **A** покращує chroma на +6…+12 dB, але при тому ж сумарному бітрейті втрачає luma (−3.4 dB @4M) і
  edge-SSIM: 30 % бітів іде у aux-вид, а «chroma як luma» у aux погано стискається (розриви на межах
  8-рядкових смуг U/V). На 8M luma майже рівна базовому. Кодування — 2× (два енкодери).
- **B** дає майже ідеальну chroma на тексті при нульовій ціні у відеопотоці; ціна — одноразові
  ~95 КБ (400–1150 kbit) на повністю статичний екран, тобто ~0.1–0.3 с каналу 4 Мбіт/с. Luma не змінюється
  (зростання luma PSNR — наслідок меншого кліпінгу при RGB-перетворенні). Працює лише для статики: при
  прокрутці/зміні тайла уточнення інвалідовується і має надсилатися повторно.
- **C** найкраще за якістю, але libvpx у realtime **перевищує ціль бітрейту** (201 kbit/кадр ≈ 6 Мбіт/с
  при цілі 4) — порівняння з H.264 при «рівному бітрейті» тут нечесне; кодування ~2× x264 veryfast.

## Чи декодує Chrome VP9 profile 1?

- WebRTC (`RTCPeerConnection`): libwebrtc за замовчуванням оголошує VP9 profile 0 і (для HDR) profile 2;
  profile 1 (8-біт 4:4:4) у SDP-пропозиції Chrome, наскільки відомо, **не оголошується** — **UNVERIFIED**
  (перевірити `RTCRtpReceiver.getCapabilities('video')` у цільовій версії Chrome; джерело для перевірки —
  `webrtc/media/base/vp9_profile.h` та `SupportedVP9Codecs()` у libwebrtc).
- WebCodecs `VideoDecoder` з кодеком `vp09.01.10.08.03` (4:4:4) — ймовірно підтримується через програмний
  libvpx у Chrome, без апаратного прискорення — **UNVERIFIED** (перевірити `VideoDecoder.isConfigSupported`).
- Отже C вимагає власного транспорту (DataChannel/WebTransport + WebCodecs) замість `<video>`, і апаратне
  кодування VP9 4:4:4 на Windows-агенті (MF) практично недоступне → програмний libvpx на агенті.

## Ескіз реалізації у браузері (для A; B — спрощений варіант)

**A (AVC444):**
1. Транспорт: два кадри (main, aux) з однаковим timestamp; WebRTC `<video>` не дає синхронізованого
   доступу до двох треків → DataChannel/WebTransport з власною пакетизацією Annex-B.
2. Два `VideoDecoder` (`avc1.4D0028`, `hardwareAcceleration: "prefer-hardware"`), вихідні `VideoFrame`
   кладуться у чергу за timestamp; пара готова → рендер.
3. WebGL2: обидва кадри як зовнішні текстури (`texImage2D(VideoFrame)` — у Chrome без копії на CPU
   у більшості випадків). Фрагментний шейдер на піксель (x,y):
   - Y = main.Y(x,y);
   - парний рядок, парний стовпець: U,V = main.UV(x/2,y/2); парний рядок, непарний стовпець: aux.UV(x/2,y/2);
   - непарний рядок: r = (y−1)/2, блок b = r/8, i = r%8; U = aux.Y(x, 16b+i), V = aux.Y(x, 16b+8+i);
   - BT.709 limited → RGB. Семплінг `texelFetch`, без фільтрації (інакше змішування сусідів у aux).
   Проблема: `VideoFrame` як текстура вже конвертований у RGB драйвером → потрібен доступ до сирих
   площин: `VideoFrame.copyTo()` у NV12/I420 (копія GPU→CPU ~3 МБ/кадр 1080p) + `texSubImage2D`
   трьох площин. Це головна вартість.
4. CPU-оцінка (1080p30, UNVERIFIED, оцінка, не вимір): 2× апаратне декодування ≈ 0 CPU; `copyTo` 2×3.1 МБ
   + завантаження текстур ≈ 2–4 мс/кадр на одне ядро (≈ 6–12 % ядра при 30 fps); шейдер — GPU,
   <0.5 мс. При програмному декодуванні (немає HW) — +2×(4–8) мс/кадр.

**B (рекомендовано):** існуючий `<video>`/WebRTC-шлях без змін + канал уточнень (DataChannel). Тайли
приходять як PNG (Cb,Cr), декодуються `createImageBitmap`, кладуться в текстуру chroma-оверлея.
Оверлей-шейдер для тайлів з валідним уточненням бере Y з відео (потребує доступу до luma — той самий
`copyTo`, або простіше: агент шле RGB-тайл lossless цілком, і канвас просто малює його поверх відео —
ціна ~2–3× байтів, але жодних шейдерів). Інвалідація: агент знає dirty-регіони (DXGI dirty rects) →
повідомлення «тайл застарів» синхронно з кадром; уточнення шлеться після ~300 мс спокою регіону.
CPU: декодування PNG ~1 МБ раз на зміну екрана — мс, у стаціонарі ≈ 0.

## Ризики

- A: синхронізація двох потоків і відмова від `<video>`/WebRTC jitter buffer; при втраті aux-кадру —
  кольорові артефакти (треба fallback на 4:2:0 апсемпл); 2× навантаження на апаратний енкодер агента
  (у NVENC/QSV обмеження кількості сесій); програшу luma при тому ж бітрейті.
- B: тільки статика; помилка інвалідації = «застарілий колір» поверх нового вмісту (критично —
  тестувати з dirty rects); сплески трафіку при частій зміні екрана (потрібен ліміт швидкості уточнень);
  маска тексту в симуляції — проста евристика контрасту.
- C: VP9 p1 у WebRTC Chrome — UNVERIFIED/ймовірно ні; немає апаратного VP9 4:4:4 кодування на
  типовому Windows-агенті; libvpx realtime тримає бітрейт гірше; CPU агента ~2× x264.
- Загальне: результати на синтетичному корпусі, без реального апаратного енкодера.

## Рекомендація

**Варіант B — 4:2:0 Main потік без змін + lossless-уточнення chroma (або RGB) тайлів тексту для
статичних регіонів.** Він дає найкращу chroma на тексті (≈69–73 dB проти 39–40 dB базового і 45–52 dB
у A) без зміни бітрейту відеопотоку і без ризиків транспорту/кодека, сумісний з поточним Chrome WebRTC
шляхом; ціна — ~95 КБ одноразово на статичний екран. A відкласти (складність ≫ виграш при тому ж
бітрейті), C — лише як майбутній експеримент після перевірки підтримки VP9 profile 1 у Chrome.
