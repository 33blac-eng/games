# oo-agent — T2 живий агент

Склеює готові модулі в один пайплайн і не дублює жоден з них:

```
agent/capture (DXGI, zero-copy: SetCPUReadback(false))
        │ ID3D11Texture2D (NV12)
        ▼
agent/encode  (hardware MFT, той самий D3DDevice)
        │ []AU{Data, Keyframe, PTS}
        ▼
транспорт (-transport wt|webrtc, обидва кандидати в одному бінарі)
```

## Запуск

```
oo-agent -transport wt     -hub localhost:4460                    -fps 60 -bitrate 8000000
oo-agent -transport webrtc -hub http://127.0.0.1:4470/offer/agent -fps 60 -bitrate 8000000
```

Прапорці: `-transport wt|webrtc` (дефолт `wt`), `-hub` (дефолт залежить від
транспорту), `-fps 60`, `-bitrate 8000000`, `-width/-height` (дефолт
1920x1080 — енкодер сам масштабує з нативної роздільності через
`Config.SrcWidth/SrcHeight`), `-output 0` (індекс DXGI-виводу на старті;
неіснуючий індекс клампиться до 0, а не валить агента), `-switch-addr`
(локальний HTTP для перемикання монітора, див. нижче).

Windows-only (build tag). `main_stub.go` тримає `GOOS=linux go build ./agent/...`
зеленим.

## Токен агента (SEC #17, #33)

Хаб приймає **токен ноди**: `hex(HMAC-SHA256(master, node_id))`. Випускає його
`oo-node-token` на хабі (master — `OO_SCREEN_AGENT_SECRET`, без нього —
`OO_SCREEN_T1_TOKEN`):

```
OO_SCREEN_AGENT_SECRET=... go run ./hub/cmd/oo-node-token -node <node_id> > agent.token
```

Агент читає токен (перший знайдений):

1. `-token-file C:\ProgramData\oo-screen\agent.token` — **рекомендовано**;
2. env `OO_AGENT_TOKEN`;
3. `-token <рядок>` — лише сумісність: видно в командному рядку schtask будь-
   якому локальному користувачу, агент пише WARNING;
4. env `OO_SCREEN_T1_TOKEN` (легасі).

ACL файла — лише SYSTEM і Administrators:

```
icacls C:\ProgramData\oo-screen\agent.token /inheritance:r /grant:r SYSTEM:R Administrators:F
```

Задача планувальника: `oo-agent.exe -node <node_id> -token-file C:\ProgramData\oo-screen\agent.token ...`
(без `-token`). Відсутній чи порожній `-token-file` — агент не стартує (а не
тихо падає на слабше джерело).

## Admission-політика (§5.5)

Один активний `send` за раз (`inFlight` atomic-прапорець, встановлюється
перед запуском sender-горутини і знімається нею по завершенню). Якщо
попередній `send` ще не завершився коли прийшов наступний захоплений кадр —
кадр дропається **до** `Encode` (енкодер його взагалі не бачить). Тому:

- референсні кадри енкодера лишаються цілі (ми нічого йому не подавали) —
  **IDR після дропу не потрібен**, всупереч інтуїції "пропустили кадр,
  треба ключовий";
- лічильник дропів логується не частіше раз/5с разом із `sent`;
- статичний екран (`capture.NextFrame` внутрішньо крутиться на
  `OOS_TIMEOUT`, у виклик `oo-agent` це не просочується) просто не породжує
  нових ітерацій циклу — нічого не шлється, нічого спеціального робити не
  треба.

## Реконект

Втрата транспорту (помилка `send`, доставлена через `txErrCh`) → цикл
`reconnect()` з експоненційним бек-офом (200мс → 5с стеля) → після
успішного передзʼєднання `Encoder.ForceIDR()`, бо стан декодера на іншому
боці втрачено. `Ctrl+C`/SIGTERM → `context` скасовується, цикл виходить
чисто, `capture`/`encode`/транспорт закриваються через `defer`/`close()`.

## PTS / seq

- `captureSeq` — лічильник ВХІДНИХ кадрів (не дропнутих), драйвить
  `encode.Frame.PTS = captureSeq * (1s/fps)`. Не плутати з номером кадру
  захоплення — дропнуті кадри в нього не потрапляють, бо до `Encode` не
  доходять.
- `au.PTS`, що повертає енкодер, належить кадру, який його породив
  (конвеєр асинхронний — README `agent/encode` каже орієнтуватись саме на
  `au.PTS`, не на порядок виклику `Encode`).
- `seq` (envelope `FrameSeq`, тільки WT) — монотонний номер ВІДПРАВЛЕНОГО
  AU, окремий від `captureSeq`.
- WebRTC не використовує envelope: `Duration` для `media.Sample` рахується
  як дельта між `au.PTS` двох послідовних AU (не фіксований 1/fps), бо живе
  захоплення не метрономне.

## Відомі межі

- **Порт хаба фіксований константою в `-hub`-дефолтах** (4460 для wt,
  4470 для webrtc) — якщо порт зайнятий іншим бенчем, живий прогін неможливий
  без зупинки того бенчу; агент сам порт не міняє.
- **Немає внутрішнього rate-limit на дропи**: якщо транспорт стабільно
  повільніший за захоплення, `oo-agent` дропатиме майже кожен кадр — це
  видно з логу (`dropped` росте, `sent` — ні), але саме по собі не є
  помилкою: це і є §5.5 у дії.
- **`-width/-height` не перевіряють, що GPU взагалі кодує таку роздільність.**
  За README `agent/encode`, деякі GPU (напр. Kepler-NVENC) не кодують вище
  1080p — `encode.New` поверне помилку, `oo-agent` завершиться з `log.Fatalf`.
- **Перемикання монітора керується тимчасовим локальним HTTP**, бо в
  `internal/control` немає типу під нього. Коли він зʼявиться, `-switch-addr`
  прибирається, а `stream.SwitchOutput` лишається як є.
- **Список моніторів їде лише в WebRTC-offer.** У WT-ноги offer-а немає, тож
  там він тільки в лозі старту.

## Перемикання монітора на льоту

```
oo-agent ... -switch-addr 127.0.0.1:4480
curl 127.0.0.1:4480/outputs                  # {"outputs":[{"index":0,...}],"active":0}
curl -X POST "127.0.0.1:4480/output?i=1"     # або ?i=next
```

Запит лише КЛАДЕТЬСЯ в чергу; перемикає його кадровий цикл (капчер не
thread-safe). Успіх у лозі:
`switched to output 1 (native ..., encode ..., epoch=2)` — епоха зсувається,
бо інша геометрія несе інший SPS. Неіснуючий індекс не перериває потік:
`switch output -> 1: виходу 1 не існує: на цьому ПК їх 1 (0..0)`, і `sent=`
далі росте.

Список моніторів агент кладе в offer (`outputs`, `active_output`) — тим самим
шляхом, що стартовий `bitrate`.
