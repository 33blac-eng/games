# oo-screen: що доробити до 10/10

Дата: 03.10.2026. Основа: `COMPARISON.md` (32 параметри) і код гілки `claude/confident-tesla-x4f240`.
Оцінка «зараз» — моя експертна, 0–10, відносно найкращого з лідерів за цим параметром.
Зусилля: S — дні, M — 1–3 тижні, L — місяць і більше.

> **Оновлено 06.10.2026** за `WORLD-COMPARISON-2026.md` (техніки лідерів для тексту й затримки, перевірені за сирцями).
> Змінено рядки 5, 6, 10, 11, 14, 19 і додано **Частину C** — пріоритетний топ-10.
> Головна поправка: Chrome через WebRTC **декодує** 4:4:4 — H.264 High 4:4:4 Predictive (`f4001f`), VP9 profile 1 і AV1 profile 1, усе програмно.
> Отже, справжнє обмеження — енкодер агента (MFT не вміє 4:4:4), а не браузер.

## Частина B. Параметри, які ми в порівнянні опустили

Ці параметри не увійшли до 32, але вони важливі для оцінки «10/10». Для конкурентів їх не досліджували.

### B1. Надійність і експлуатація
| Параметр | Зараз | Що зробити |
|---|---|---|
| Час до першого кадру | Не міряли | Метрика + ціль < 1 с (кеш GOP уже допомагає) |
| Час перепідключення після обриву | Є реконект із бек-офом, не міряли | Метрика + ціль < 2 с, тест з netem |
| Доступність хаба (uptime), відмовостійкість | Один хаб, без резерву | Кілька хабів + балансування, перенесення сесії |
| Масштабування | Не міряли | Навантажувальний тест: скільки ПК і глядачів тримає один хаб (є `hub/cmd/loadgen`) |
| Спостережуваність | Логи, pprof | Метрики Prometheus (бітрейт, втрати, RTT, FPS, затримка на сесію), дашборд, алерти |
| Автооновлення агента | Немає (скрипт-чернетка) | Підписане автооновлення з відкатом, викатка хвилями |
| Підписування бінарників | Немає | Code signing агента (Windows SmartScreen, антивіруси) |

### B2. Ресурси на хості
| Параметр | Зараз | Що зробити |
|---|---|---|
| CPU/GPU агента | Частково (swlimit) | Заміри на слабкому ПК: ціль ≤ 25 % CPU у статиці, ≤ 50 % у русі (з ТЗ) |
| Пам'ять агента | Не міряли | Тест на витоки 24 год |
| Трафік у статиці | ~1.5 кбіт/с (прод) | Добре; зберегти |
| Трафік на типовій роботі (Excel, браузер) | Не міряли | Метрика кбіт/с на годину роботи |

### B3. Якість у роботі
| Параметр | Зараз | Що зробити |
|---|---|---|
| Плавність (рівномірність кадрів) | Не міряли | Метрика jitter між кадрами в плеєрі |
| Синхронізація звуку й відео | Не міряли | Тест A/V sync (±40 мс) |
| Точність кольору | BT.709 прописано | Перевірити на темних темах і градієнтах |
| Відео на віддаленому ПК (YouTube) | Не перевіряли | Режим «Відео»: 60 к/с, більше біт |

| Параметр | Зараз | Що зробити |
|---|---|---|

## Порядок робіт (рекомендація)

1. **Спершу перевірити те, що вже зроблено**, на реальних ПК (Windows + Chrome): дошліфування, пропуск кадрів, курсор, тайли, програмний енкодер. Без цього решта — на піску.
2. **Швидкі виграші (S):** Opus замість PCMU, буфер обміну, ролі глядачів, pacer, стеля бітрейту, метрики Prometheus.
3. **Мережа (M):** TWCC + GCC, FEC, intra-refresh, TCP/TLS 443 як запасний шлях.
4. **Функції (M):** власний канал вводу в плеєрі, файли, мікрофон, усі монітори, згода/індикатор/аудит.
5. **Великі (L):** 4:4:4 у русі — спершу H.264 `f4001f` (Частина C, C4 → C7), VP9/AV1 лише як запасний варіант; P2P; macOS/Linux-хости.
6. **Якість тексту й затримка (06.10):** C1, C2, C3 і C5 — одразу (S, ризик низький); C4 перед будь-яким рішенням про 4:4:4.

Свідомо можна не робити (не потрібно для офісу): HDR/10-біт, геймпади, друк.
